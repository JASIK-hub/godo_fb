# Требования к отдельному ML-репозиторию

Это интеграционные требования, не описание проверенной реализации ML.

Backend поддерживает также асинхронный ML API: POST `/api/v1/analyze` возвращает `{ "job_id": "..." }` (опционально `status: queued | processing`), затем backend каждые 2 секунды отправляет GET `/api/v1/jobs/{job_id}` с тем же `X-API-Key` из `ML_API_KEY`. Путь jobs строится рядом с настроенным inference endpoint. Статусы `queued` и `processing` продолжают ожидание; `completed` или `done` завершают его, результат читается из `result` (либо из верхнего уровня). `failed` завершает задачу ошибкой. POST и все GET используют общий `ML_TIMEOUT_MS` и дедлайн задачи. Браузер продолжает опрашивать `/api/site/jobs/{job_id}` с локальным идентификатором; ML-ключ остаётся на backend.

1. Передать готовый Linux container image с неизменяемым digest, запускаемый собственным ENTRYPOINT, портом и путями health/inference. Compose не задаёт выдуманную команду запуска. Приложение должно слушать `0.0.0.0`; defaults backend: `http://ml:8000/analyze`, `http://ml:8000/health`.
2. `POST` inference принимает multipart `file`, optional `X-API-Key` с отдельным ML-ключом. `X-Job-Id` — UUID для корреляции/дедупликации, `X-Deadline-At` — абсолютное UTC-время. Часы хостов должны быть синхронизированы. Backend не повторяет вызов.
3. POST может вернуть готовый результат либо задачу `{"job_id":"...","status":"processing"}` (допускаются queued/pending/running или только job_id). Для асинхронного ответа backend опрашивает GET по тому же адресу сервиса, заменяя конечный /analyze на /jobs/{job_id}. Например /api/v1/analyze → /api/v1/jobs/{job_id}. Интервал ML_POLL_INTERVAL_MS (по умолчанию 1000); общий ML_TIMEOUT_MS включает загрузку, ожидание и все опросы. Отправляются тот же ML-ключ и корреляционные заголовки. Публичный job_id backend остаётся собственным.
   Завершение: `{"job_id":"...","status":"completed","result":{"verdict":"no_violation","violations":[]}}`. Также принимается status done с result. verdict violation преобразуется в fail, no_violation в pass. Синхронный старый формат pass/fail с code/message/timestamp_seconds поддерживается.
   В новом формате нарушение содержит type, description, timecode_sec, необязательные rule_id, evidence_frames: [{timestamp_sec,image_base64}] и rule: {title,section,url}. Backend сохраняет описание, тип, источник и кадры; при отсутствии rule_id поле code содержит type и не является подтверждением юридического сопоставления. Источники не генерируются.
   Пустой violations допустим только для no_violation/pass. Таймкоды должны быть в пределах видео. Лимиты: 16 MiB всего ответа, 1000 событий, описание 4096 символов, не более 3 JPEG-кадров на событие с base64 до 2 MiB каждый. assessment_file — локальный путь ML: не читается, не скачивается и не передаётся браузеру.
4. Ошибка обработки/нет доступной модели/не декодируется видео → non-2xx, никогда не `no_violation`. Backend возвращает failed. Readiness 2xx только после загрузки всех весов и справочника, доступности ускорителя и возможности принимать анализ.
5. Собственная очередь и параллельность должны соответствовать ресурсам. Дедлайн включает ожидание у ML. При отключении клиента или истечении дедлайна прекратить вычисления, освободить GPU и временные файлы. Если библиотека не поддерживает отмену, изолировать анализ в управляемом процессе либо предложить отдельный cancel endpoint с подтверждением остановки. До этого ограничения backend не гарантируют отсутствие оставшихся GPU-вычислений.
6. Веса и нормативный справочник заранее доступны в read-only `/models` и `/rules/rules.json`. Использовать `MODEL_WEIGHTS_PATH` и `RULES_PATH`, `local_files_only`/эквивалент библиотеки, запрет авто-download и внешних AI API. Все дополнительные tokenizer/config/encoder assets также должны быть внутри образа или каталога. Health и первая задача должны работать после холодного старта без интернета. ML-артефакты не должны зависеть от пользовательского home cache.
7. Справочником и его форматом хранения управляет ML. ML проверяет существование rule_id и достоверность нормативного источника. Backend не читает справочник и не требует RULES_PATH. Синтетический пример удалён из backend. Источник передаётся в message или в необязательном rule; достоверность источника обеспечивается ML.
8. Публичный API сохраняет status done и verdict pass/fail; добавлены необязательные type, evidence_frames и rule. UI показывает inline JPEG и источник. Внешние изображения не скачиваются; старое непустое frames отклоняется. Ошибка ML analysis_inconclusive отображается как ML_INCONCLUSIVE и требует проверки человеком, не превращается в no_violation. Отсутствие нарушений относится только к реально проверенным ML критериям; backend не выводит дополнительные нарушения из assessment_file.
9. Передать требования CPU/RAM/VRAM, версию CUDA/драйвера/NVIDIA Container Toolkit и проверенный GPU Compose override именно для своего образа. В этом репозитории намеренно нет `gpus: all` без подтверждения совместимости. Если нужен рабочий каталог, описать права и retention; не монтировать сокет Docker/каталоги хоста и не использовать host networking.
10. Предоставить manifest SHA256 весов, образа и справочника и измерения на согласованных синтетических/разрешённых локальных роликах: кодек, размер, длительность, параллельность, время queue/decode/inference/total. Не отправлять видео/кадры/описания облачным AI для этих проверок.

Проверка локальности: после staging образов/весов выполнить процедуру из README и `node deploy/check-offline.mjs`. Проверить также холодный старт ML без сети, уничтожив только его временный cache (не веса), и повторить тест. Дополнить сетевым capture/audit хоста: три probes не являются полной экспертизой всех зависимостей.
